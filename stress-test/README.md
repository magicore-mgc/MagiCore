# MagiCore Stress Matrix

The stress matrix reads `mgc capabilities --json` from the binary under test and creates every advertised core/framework row in isolated temporary storage. It fails when a command exits unsuccessfully, the core/framework identity is wrong, metadata is invalid, or the scaffold has no non-empty source/manifest/automation payload. It records JSON evidence for CI.

Run it after building the CLI:

```sh
python3 stress-test/test/test_stress_matrix.py
python3 stress-test/src/stress_matrix.py --binary target/debug/mgc --report stress-test-report.json
```

The runner walks every command and nested subcommand advertised by `mgc --help`, invokes each help path, and rejects a malformed or failing command tree. It also passes an intentionally unknown option to every discovered command path and requires the CLI parser to reject it. For every scaffold row it records optimizer, cache, security-audit, shared-store scope, and empty-graph V3/V4 lock replay results. Native install runs before the isolated quality probes, so an audit sees the lock produced by that fixture. The stress fixture deliberately removes declared packages before install: a successfully installed empty graph is `not_applicable` for package scanning, and a lane without an MGC-native resolved graph is also not presented as a successful audit. A missing scanner/runtime does not become a support claim. Non-empty audit behavior is qualified by the dedicated audit E2E suite, which the stress workflow runs with OSV connectivity required. Installs and replays use the owning `install-<core>` route (for example, `install-web`). V3 is exercised for every row whose declared install owner is `mgc-native`; V4 is exercised through schema-aware Web/Lib/App writers, including the native AI Python, Bevy, ESP32-Rust, CDK, and Pulumi routes. Other rows retain explicit `unsupported` evidence. Successful empty Flutter/Swift installs that intentionally create no lock retain `not_applicable` evidence. The writer set must change with adapter wiring and integration evidence. Use `--require-full-evidence` to fail on unresolved applicable optimizer/security rows; explicit `unsupported` and `not_applicable` evidence stays visible without being counted as successful support. Use `--require-lockfile-evidence` to require one empty-graph V3/V4 result per framework and verified replay for each declared native writer.

Report schema 7 includes every framework's declared owner for all 14 dependency operations and per-core operation counts, a source-language/file-format inventory extracted from each generated scaffold, source commit, clean-tree state, binary SHA-256, universal-support gate status, blocker list, and a hash-bound native lifecycle sidecar summary. The language inventory is scaffold evidence only and explicitly does not claim that a language runtime or framework command was executed. Ownership is sourced from `mgc capabilities --json`; `framework_runtime_verified` becomes true only when real CLI install/run/test/build/dev evidence exists for every framework. The lifecycle sidecar covers only 18 native web lanes and requires 90 unique operation records tied to the exact tested binary; an absent or partial sidecar cannot establish support. The universal gate matches language evidence to each scaffold's emitted languages and requires one verified runtime/parser probe for every standalone language; framework-only formats remain dependent on per-framework lifecycle evidence. `passed` counts contract checks, including correct refusals; `verified_evidence` counts only successful verified checks. Unverified, unsupported, and not-applicable evidence remain separate.

The run/test smoke injects a tiny Python script into the scaffold and empties declared dependency sections in the isolated fixture before invoking `mgc run` and `mgc test`. It verifies MGC's script orchestration and environment contract. Separate dependency-free probes use a minimal project under the isolated MagiCore data root: configured Node/TypeScript, Python, Go, Dart, Rust, Swift, Bash, C/C++, C#, Java/Kotlin, PHP, Objective-C/Objective-C++, Zig, and GDScript profiles run through `mgc run`; Terraform HCL is checked with Terraform's formatter/parser. This proves only that a source runtime starts through MGC or that HCL parses; it does not execute generated framework source or the framework's own CLI, dev server, build, or test suite, and it does not satisfy the strict framework-runtime evidence gate. Missing profiles or toolchains remain explicitly unverified. Native install is attempted only for rows whose declared install owner is `mgc-native`; a declared owner is still not runtime proof. Lockfile checks pin the fixture to V3, verify frozen replay preserves bytes, then repeat the write/replay check with V4 on wired cores.

The GitHub Actions workflow runs on Linux, macOS, and Windows. It scaffolds every advertised row and enforces the declared optimizer/security, standalone language-runtime, and lockfile evidence contracts. Every advertised framework must have verified language/runtime, CLI lifecycle, optimizer, cache, security, shared-store and V3/V4 lock evidence; every dependency operation must be MGC-owned. Unsupported, not-applicable, missing and unverified results keep the gate red. Release publication depends on this workflow and its finite product E2E lanes, not on universal support across every advertised framework. CI also runs the lockfile integration suites and a non-empty CLI V4 lifecycle (`add`, frozen install, `update`, `remove`) against a local npm fixture. Its optimizer/audit E2E step sets `MGC_E2E_AUDIT_NETWORK=required`, so OSV-dependent tests cannot silently skip when the endpoint is unreachable. It runs real install/frozen-install/run/test/build/dev E2Es for all 18 native JS web framework lanes: 11 in the consolidated matrix and 7 dedicated frontend targets. A separate backend route E2E covers all 12 advertised non-JS web backend rows with empty-graph V3/V4 install and frozen replay, asserting that `.mgc.core` remains `web`; another non-empty lifecycle E2E covers Python, Rust, Go, Java, and .NET on V3 and V4. FastAPI now has a networked native install/dev HTTP lifecycle test built with the single-core Web feature, and the synthetic Python import E2E runs under the single-core AI feature. These checks do not establish backend dev/build/test support for every backend framework. The Lib adapter's selection of Web security policy has a separate unit test. The JS suites append machine-readable records to a fresh per-job sidecar; the stress report validates the suite/lane mapping, requires exactly one record for each of the five operations per lane, binds every record to the tested CLI binary, and uploads the report plus sidecar together. Dedicated JS targets run in a loop that continues after a lane fails, so CI records later framework results too. The AI V4 E2E installs a verified local wheel, imports it with real Python through `mgc run`, preserves frozen lock bytes, and rejects a tampered artifact URL. The matrix isolates `HOME`, `MGC_DATA_DIR`, `MGC_CACHE_DIR`, `MGC_TEMPLATES_DIR`, language-toolchain caches, and temporary files beneath a temporary root. The stress runner's generic synthetic script checks remain orchestration evidence; framework E2Es and the lifecycle matrix provide framework-specific runtime evidence. A global store route whose managed roots are safe but lacks a package-bearing fixture is recorded as `passed=true`, `evidence_status=unverified`: the route check succeeded, while non-empty package runtime is still unproven; the strict universal diagnostic keeps the gap visible.

## Universal support gate

`--require-full-evidence` and `--require-lockfile-evidence` validate the currently declared scope; they intentionally allow explicit unsupported and not-applicable rows. They do not mean every framework is supported. The stricter readiness mode is:

```sh
python3 stress-test/src/stress_matrix.py \
  --binary target/debug/mgc \
  --report stress-test-report.json \
  --require-full-evidence \
  --require-lockfile-evidence \
  --require-universal-support
```

The opt-in strict mode below still asks whether every advertised framework/language row has universal lifecycle evidence; it is diagnostic and is expected to remain blocked while rows are explicitly unsupported or unverified. PR and release workflows enforce the finite E2E scope they actually run, plus the declared optimizer/security, standalone language-runtime, and lockfile evidence checks. Generated source files and synthetic Python sentinels do not count as framework lifecycle evidence; declarations, expected refusals, empty graphs, `unsupported`, and `not_applicable` remain separate evidence statuses. A green finite-scope workflow must not be described as universal framework support.

The current 86-row baseline is not universal support. All 86 scaffold commands generated a project with a recognized source or automation file. Reports v41/v43 declare native install ownership for 48 rows and explicitly unsupported install routes for 38. The table is sourced from report v43:
